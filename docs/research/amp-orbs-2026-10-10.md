# Amp Orbs: current product and migration assessment

Date: 2026-10-10

## Bottom line

Amp Orbs are persistent-per-thread, isolated Linux development machines managed by Amp. A new thread gets a fresh machine with the repository, tools, plugins, and thread context; it can keep working after the user's computer disconnects, pause when idle, and later wake with its filesystem and services intact. The main pitch is not raw VM hosting. It is one complete, reviewable development environment per task, with the agent, diff, files, terminal, previews, and conversation all reachable from the web, CLI, macOS, or iOS. ([Orbs overview](https://ampcode.com/docs/orbs), [What Are Orbs?](https://ampcode.com/what-are-orbs))

For an ordinary GitHub-hosted Node, Python, Go, Rust, or similar project that already installs and tests reproducibly on Linux, the first useful Orb is likely a short onboarding exercise: connect GitHub, create a project, start a thread, then add a small executable `.agents/setup`. A web app normally adds `.amp/services.yaml` so Amp can supervise and expose its development server. ([Getting Started](https://ampcode.com/docs/orbs/getting-started), [Customizing Orbs](https://ampcode.com/docs/orbs/customizing), [Portals](https://ampcode.com/docs/orbs/portals))

The hard part is exactly what makes cloud development hard elsewhere: undocumented laptop state. Private networks, local databases and fixtures, browser OAuth, private registries, multiple repositories, Docker, or OS-specific workflows all work only after those dependencies are made explicit. Amp's own case study describes a 428-line setup script, seeded test users, dev-only magic login, a machine-readable preflight, and centralized logs for its large application. That is evidence that Orbs can support a complex system, but also that the migration cost scales with how much implicit environment and authentication state the application has. ([Putting an Agent in an Orb](https://ampcode.com/notes/putting-an-agent-in-an-orb))

## What an Orb buys you

- **Parallelism without local worktree and port management.** Each Orb thread has its own machine, checkout, filesystem, and services, so independent tasks do not compete for the user's CPU, disk, ports, or working tree. Amp currently allows a burst of 20 metered Orb starts per user; after that it starts one additional Orb every five minutes and queues later requests. ([Orbs overview](https://ampcode.com/docs/orbs))
- **A task keeps running independently of the client.** `amp -ox` creates an execute-mode Orb thread, prints its URL, and exits immediately; the agent continues remotely. The same thread can be continued from the web, CLI, or another device. ([Spawning Orbs](https://ampcode.com/docs/cli/spawning-orbs))
- **The review environment stays attached to the work.** The thread UI includes the change set, file browser, a shared tmux terminal, and authenticated Portal URLs for HTTP services. Portal review comments can point at an element on the running page and send its page/source context back to the agent. ([Orbs overview](https://ampcode.com/docs/orbs), [Portals](https://ampcode.com/docs/orbs/portals))
- **The environment survives idle periods.** A paused Orb costs nothing and later wakes with its filesystem and services. The Orb's filesystem and memory remain encrypted at rest until the thread is deleted; deleting the thread deletes its Orb. ([Sizes & Costs](https://ampcode.com/docs/orbs/sizes-and-costs), [Security Reference — Orb Data](https://ampcode.com/security#orb-data))
- **Delivery is integrated.** The Changes pane can ship directly to the base branch, push a feature branch, or run a custom delivery prompt. `amp sync <thread>` can mirror the Orb's changes into a local checkout while the remote agent continues. ([Shipping Changes](https://ampcode.com/docs/orbs/shipping), [Orbs overview](https://ampcode.com/docs/orbs#sync-changes-to-your-computer))
- **It supports more than one agent.** A thread can schedule future work, react to webhooks, collaborate with teammates, and spawn agents in other Orbs that return messages or files. ([Orbs overview](https://ampcode.com/docs/orbs), [Orbs, Explained](https://ampcode.com/notes/orbs-explained))

## Product status, access, and pricing

Orbs are a current, generally offered Amp feature rather than a closed preview. Amp's pricing page offers them on Hobby as pay-as-you-go usage, and includes Orb allowances with the paid individual tiers. The native macOS/iOS apps are described as beta, and computer use inside Orb Desktop is explicitly early and unsupported. ([Pricing](https://ampcode.com/pricing), [macOS and iOS](https://ampcode.com/docs/macos-and-ios), [Orb Desktop](https://ampcode.com/docs/orbs/desktop))

Current public individual pricing is:

| Tier | Monthly price | Advertised allowance at `a1.small` |
| --- | ---: | ---: |
| Hobby | Free | Pay as you go |
| Megawatt | $20 | 45,000 minutes |
| Gigawatt | $200 | 480,000 minutes |

The live pricing page's detail popover shows that the minute allowance is size-weighted: Megawatt's 45,000 `a1.small` minutes become 90,000 on `a1.tiny`, 22,500 on `a1.medium`, or 5,625 on `a1.xxlarge`; Gigawatt's corresponding `a1.small` figure is 480,000. The page also says Teams add no separate team charge and Enterprise pricing is custom. Agent/model usage and Orb compute are separate allowances. ([Pricing](https://ampcode.com/pricing), [pricing documentation](https://ampcode.com/docs/pricing))

Orb compute is metered by the minute. Every listed size has 60 GB of disk:

| Size | CPU | Memory | Standard price |
| --- | ---: | ---: | ---: |
| `a1.tiny` | 1 | 2 GB | $0.08/hour |
| `a1.small` | 2 | 4 GB | $0.17/hour |
| `a1.medium` | 4 | 8 GB | $0.33/hour |
| `a1.large` | 8 | 16 GB | $0.66/hour |

| `a1.3xlarge` | 16 | 44 GB | $2.13/hour |

`a1.3xlarge` is restricted to Gigawatt subscribers and Enterprise workspace members. An Orb pauses when the agent has done no work for five minutes and the user has not interacted for twenty minutes; a running service by itself does not keep it awake. Archiving a thread pauses it immediately. ([Sizes & Costs](https://ampcode.com/docs/orbs/sizes-and-costs))

## Onboarding process

1. **Sign in to Amp.** The web workflow does not require a local installation. A private GitHub repository requires connecting GitHub in Amp settings; the user authorizes Amp and installs the Amp GitHub App on the owning account or organization, scoped to all or selected repositories. ([Getting Started](https://ampcode.com/docs/orbs/getting-started#1-sign-in), [GitHub & Git](https://ampcode.com/docs/github#connect-github))
2. **Create an Amp project.** Select a connected GitHub repository, paste any public HTTPS Git URL, supply credentials for a private non-GitHub host, or start with an Amp-hosted blank repository. Pick personal or workspace ownership, a base branch, a default Orb size, and optionally additional repositories. A thread can also use **No Project** for research or one-off scripts. ([Projects](https://ampcode.com/docs/projects#create-a-project), [Getting Started](https://ampcode.com/docs/orbs/getting-started#2-create-a-project))
3. **Start a thread with `New Orb` as its executor.** The equivalent CLI command is `amp -ox "prompt"`; from a checkout the CLI matches Git remotes to an Amp project, and `--project` selects one explicitly. `amp --executor orb` opens the interactive TUI with a new Orb selected. ([Getting Started](https://ampcode.com/docs/orbs/getting-started#3-send-a-prompt), [Spawning Orbs](https://ampcode.com/docs/cli/spawning-orbs))
4. **Make the repository repeatable.** Commit an executable `.agents/setup` for dependency/tool installation and, only if needed, `.agents/resume` for quick authentication or repair after activation and each wake. Amp offers a **Set Up with Amp** flow that asks the agent to create, run, verify, and commit both hooks. ([Getting Started](https://ampcode.com/docs/orbs/getting-started#4-prepare-the-repository-for-orbs-optional), [Customizing Orbs](https://ampcode.com/docs/orbs/customizing))
5. **Declare long-running services.** Commit `.amp/services.yaml` for development servers, databases, or other supervised processes; add Portal metadata when a service should be exposed in the thread. ([Portals — Define Services](https://ampcode.com/docs/orbs/portals#define-services))
6. **Configure secrets and environment variables.** Values may be workspace-, project-, or personal-scoped, with personal overriding project and project overriding workspace. Prefer temporary Orb OIDC identity where the target service supports it. ([Handling Secrets](https://ampcode.com/docs/orbs/handling-secrets))
7. **Run, review, and deliver.** Use the Files, Terminal, Changes, and Portal panes; then Ship, push a branch/PR, use a custom ship prompt, or synchronize the changes locally. ([Orbs overview](https://ampcode.com/docs/orbs), [Shipping Changes](https://ampcode.com/docs/orbs/shipping))

Amp's official getting-started page includes a 14:38 screencast taking a Laravel repository to a working Orb. It demonstrates the intended low-ceremony path, but it should not be treated as a guaranteed setup time for an arbitrary repository. ([Getting Started](https://ampcode.com/docs/orbs/getting-started))

## Environment and configuration model

There is no large container specification or bespoke infrastructure manifest to adopt. The durable, repository-owned surface is deliberately small:

| File | Role |
| --- | --- |
| `.agents/setup` | Executable, idempotent shell script that prepares a new Orb and its reusable project snapshot |
| `.agents/resume` | Optional quick authentication/repair hook after first activation and every wake |
| `.amp/services.yaml` | Declarative supervised service commands, working directories, ports, environment, health checks, platform filters, and Portal links |
| `.amp/settings.json` | Optional repository-visible Amp/MCP configuration |

The lifecycle and file responsibilities are documented in [Customizing Orbs](https://ampcode.com/docs/orbs/customizing), [Portals](https://ampcode.com/docs/orbs/portals#put-each-responsibility-in-the-right-file), and [MCP Servers in Orbs](https://ampcode.com/docs/customize/mcp#mcp-servers-in-orbs).

A minimal setup can be as small as:

```bash
#!/usr/bin/env bash
set -euo pipefail

corepack enable
pnpm install --frozen-lockfile
```

A minimal HTTP service can be:

```yaml
services:
  web:
    command: pnpm dev -- --host 0.0.0.0 --port "$PORT"
    health: /healthz
    portal: true
```

Amp supplies `PORT` and `AMP_THREAD_ID` to every service, and `PUBLIC_URL` to services with Portal links. A Portal service must listen on `$PORT`; a health endpoint passes on HTTP 2xx or 3xx. ([Portals — Define Services](https://ampcode.com/docs/orbs/portals#define-services), [Portals — Add Health Checks](https://ampcode.com/docs/orbs/portals#add-health-checks))

## Runtime, repositories, persistence, networking, and clients

### Runtime

Hosted Orbs run Debian 12 and include Git, SSH, tmux, `amp`, `gh`, Bun, Node.js, npm, pnpm, Yarn, Python, pip, `uv`, `agent-browser`, ffmpeg, ImageMagick, jq, fzf, ripgrep, vim, and other common utilities. `amp` and `gh` are authenticated after activation. Docker is not installed by default, but Amp documents installing it from `.agents/setup` and running `dockerd` as a supervised service. ([Customizing Orbs — Installing Software](https://ampcode.com/docs/orbs/customizing#installing-software))

### Repository providers

GitHub is the first-class path: Amp's GitHub App can clone private repositories, authenticate `gh`, push branches, open pull requests, and inspect CI. Public GitHub repositories work without a connection, but writes still require the App installation and the user's normal repository permission. ([GitHub & Git](https://ampcode.com/docs/github))

Public repositories on GitLab, Bitbucket, or another Git host work from an HTTPS URL. Private non-GitHub repositories require clone credentials supplied through settings. GitHub Enterprise Server is not supported. ([GitHub & Git — Other Git Hosts](https://ampcode.com/docs/github#other-git-hosts), [Customizing Orbs — Configure Git](https://ampcode.com/docs/orbs/customizing#configure-git))

Projects can clone up to 20 additional repositories under `../repos/`. Only the primary repository's `.agents/setup` runs, so that script must initialize the additional checkouts. ([Projects — Threads and Projects](https://ampcode.com/docs/projects#threads-and-projects), [Customizing Orbs — `.agents/setup`](https://ampcode.com/docs/orbs/customizing#agentssetup))

### Secrets and identity

Secrets are injected as environment variables, hidden after save, and occurrences of their values are redacted from Orb shell output. OIDC tokens can instead provide short-lived thread, user, project, or workspace identity; the default token lifetime is ten minutes and the allowed range is one minute to one hour. ([Handling Secrets](https://ampcode.com/docs/orbs/handling-secrets))

The important caveat is that lifecycle scripts are trusted code. Amp removes its setup credential before snapshotting, but it cannot prevent a script from copying exchanged tokens, provider credentials, or login caches elsewhere in the filesystem. Credentials that require personal/thread identity belong in `.agents/resume`, not `.agents/setup`. ([Handling Secrets — OIDC](https://ampcode.com/docs/orbs/handling-secrets#oidc), [Customizing Orbs — `.agents/setup`](https://ampcode.com/docs/orbs/customizing#agentssetup))

MCP servers work in Orbs, but the Orb cannot read the user's local `~/.config/amp/settings.json`. Amp recommends bundling MCP definitions in repository skills, committing them in `.amp/settings.json`, or using remote MCP definitions. Browser-based OAuth is unavailable inside Orbs, so remote OAuth must be handled through Amp or replaced with environment-token/OIDC authentication. ([MCP Servers in Orbs](https://ampcode.com/docs/customize/mcp#mcp-servers-in-orbs))

### Persistence

An individual thread keeps its Orb filesystem and memory while paused. A new thread gets a fresh environment, usually restored from a per-project, per-size snapshot produced after successful setup. Amp may reuse a matching snapshot for up to 72 hours. Changing `.agents/setup` alone does not invalidate an existing snapshot, so an immediate rollout requires deleting the cached snapshot in project settings or with `amp projects snapshots delete`. ([Customizing Orbs — lifecycle](https://ampcode.com/docs/orbs/customizing#the-orb-lifecycle), [Security Reference — Orb Data](https://ampcode.com/security#orb-data))

Manual software installs in a terminal affect only that Orb. Put them in `.agents/setup` for future threads. Uploaded or generated files remain in the Orb unless they are committed, attached to a reply, or published. ([Customizing Orbs — Installing Software](https://ampcode.com/docs/orbs/customizing#installing-software), [Files & Attachments](https://ampcode.com/docs/orbs/files-and-attachments))

### Networking and services

Portals expose HTTP services through authenticated HTTPS URLs and support temporary public sharing for one hour, three hours, one day, or seven days. They are not arbitrary public TCP forwarding. Separate frontend and API Portal hosts also have a documented limitation: browser CORS preflight requests do not carry Portal authentication, so Amp recommends exposing the frontend and proxying API requests through its development server. ([Portals](https://ampcode.com/docs/orbs/portals), [Portals — Connect Declared Services](https://ampcode.com/docs/orbs/portals#connect-declared-services))

Private network access is not implicit. Amp documents joining an Orb to Tailscale from `.agents/resume`, including an OIDC-based temporary identity and optional exit-node routing. ([Customizing Orbs — Use Tailscale](https://ampcode.com/docs/orbs/customizing#use-tailscale))

### Client and IDE experience

The primary environment is Amp's thread interface rather than a conventional remote-SSH editor. The web and native apps expose the conversation, Changes, Files, Terminal, Portals, and Desktop. The terminal shares the Orb's filesystem and tmux session with the agent. Orb Desktop is an interactive Linux desktop; Chrome starts by default and VS Code can be installed, though agent-driven computer use there is described as early and unsupported. ([Orbs overview](https://ampcode.com/docs/orbs), [Orb Desktop](https://ampcode.com/docs/orbs/desktop))

The CLI can create and detach from a thread, open an interactive Orb TUI, continue a thread by ID, stream JSON events, attach local files, and sync changes back to a local checkout. ([Spawning Orbs](https://ampcode.com/docs/cli/spawning-orbs), [Orbs overview](https://ampcode.com/docs/orbs#sync-changes-to-your-computer))

## How hard is a migration?

The following ratings are inferences from Amp's documented lifecycle and requirements, not Amp's promises.

### Easy: roughly one small setup script

A repository is a strong candidate when it has a lockfile, a deterministic install command, a clear test command, Linux-compatible dependencies, and no mandatory private-network or interactive-login dependency. Node and Python are especially well paved because their package managers and runtimes are bundled. The usual work is an idempotent `.agents/setup`, adding project secrets, and perhaps one `.amp/services.yaml` entry. Snapshot reuse makes later threads faster. ([Customizing Orbs](https://ampcode.com/docs/orbs/customizing), [Portals](https://ampcode.com/docs/orbs/portals))

### Moderate: a reproducible development environment project

Repositories that require Postgres/Redis, Docker Compose, several repositories, private registries, seeded data, or authenticated browser testing are still plausible, but the setup must install/start the dependencies and provide stable health checks, test identities, and logs. Amp's own case study says reliable setup, a single dev-server entry point, dev-only magic login, a JSON preflight, and centralized logs were what stopped the agent from guessing. ([Putting an Agent in an Orb](https://ampcode.com/notes/putting-an-agent-in-an-orb))

### Poor hosted-Orb fit

Work that intrinsically needs macOS/iOS toolchains, USB devices, special local hardware, more than 60 GB of local disk, or a GUI/keychain/browser-auth flow tied to the user's laptop is not a natural fit for hosted Debian Orbs. Amp's documented alternative for work that must run on a particular machine or network is an Amp runner. ([Orb Desktop](https://ampcode.com/docs/orbs/desktop), [Sizes & Costs](https://ampcode.com/docs/orbs/sizes-and-costs), [Runners](https://ampcode.com/docs/cli/runners))

## Migration gotchas and hard limits

- `.agents/setup` is stopped after 20 minutes; Amp continues starting the Orb but does not publish a refreshed project snapshot after a failure or timeout. ([Customizing Orbs — `.agents/setup`](https://ampcode.com/docs/orbs/customizing#agentssetup))
- Setup must be idempotent. Amp may run setup hooks more than once, and a cached snapshot can hide a newly committed setup change for up to 72 hours unless it is explicitly deleted. ([Customizing Orbs](https://ampcode.com/docs/orbs/customizing))
- Background processes launched by `.agents/setup` are killed when setup exits, including `&`, `nohup`, and `setsid` children. Put long-running processes in `.amp/services.yaml`, systemd, or a carefully designed resume hook. ([Customizing Orbs — `.agents/setup`](https://ampcode.com/docs/orbs/customizing#agentssetup))
- `.agents/resume` blocks the agent for only ten seconds; longer work continues asynchronously. It is for quick authentication/repair, not dependency installation. ([Customizing Orbs — `.agents/resume`](https://ampcode.com/docs/orbs/customizing#agentsresume))
- A printed Portal URL proves route configuration, not service readiness. Apps must bind to `$PORT`; incorrect fixed ports, host allowlists, health checks, and origin-sensitive authentication are common failure points. ([Portals — Troubleshooting](https://ampcode.com/docs/orbs/portals#troubleshooting))
- GitHub Enterprise Server is unsupported; private non-GitHub hosts need manually configured credentials. ([GitHub & Git — Other Git Hosts](https://ampcode.com/docs/github#other-git-hosts))
- An Orb cannot inherit user-local Amp/MCP settings, and browser-based MCP OAuth does not run inside it. Repository/workspace or remote configuration must replace that local state. ([MCP Servers in Orbs](https://ampcode.com/docs/customize/mcp#mcp-servers-in-orbs))
- Hosted Orb code resides on E2B ephemeral compute. Amp says its server does not store a copy of the Orb filesystem, but files the agent reads can appear in tool results and therefore become thread data. ([Security Reference — infrastructure and Orb data](https://ampcode.com/security#infrastructure-service-providers), [Security Reference — Orb Data](https://ampcode.com/security#orb-data))
- Automatic secret redaction is best-effort and does not guarantee detection of custom, encoded, or nonstandard secret formats. ([Security Reference — Secret Redaction](https://ampcode.com/security#secret-redaction))
- The default product is vendor-managed. Amp's public security page says Amp itself is not offered as a self-hosted deployment, so adopting hosted Orbs still means the Amp control plane and thread data remain a managed service. ([Security Reference — System Components](https://ampcode.com/security#system-components))

## Practical evaluation plan

The lowest-risk trial is one self-contained repository with a fast deterministic test suite and no production credentials. Create the project, let **Set Up with Amp** propose `.agents/setup` and `.agents/resume`, review the scripts, and ask one Orb to install, test, make a small change, prove it, and push a branch. If it is a web app, add one Portal service and verify that the agent can start it, authenticate as a development user, and capture evidence. This directly tests the three things that determine real adoption: cold-start reliability, ability to verify without laptop-only state, and whether the review/ship loop is better than the current local workflow. The involved product mechanisms are documented in [Getting Started](https://ampcode.com/docs/orbs/getting-started), [Customizing Orbs](https://ampcode.com/docs/orbs/customizing), [Portals](https://ampcode.com/docs/orbs/portals), and [Shipping Changes](https://ampcode.com/docs/orbs/shipping).
